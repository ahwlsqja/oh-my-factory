# Enforcement tests

Each control claim in `docs/design/2026-10-12-omf-v0-design.md` links to one test here. A claim
without a test is labeled "not enforced" in the spec.

| Test | Claim | Spec |
|---|---|---|
| `E1-metric-tamper-stops.test.ts` | An unapproved metric is never measured, an edited metric lock stops measurement, and a change to a metric's watched code, to a bands file or to `goal.md` is a regime change until J1 approves again; an edited bands hash in the goal lock stops measurement. The locked target stays in force. | §4.1, §4.2, §4.6 |
| `E2-g-canary-no-leak.test.ts` | The goal loop shows the reconciler a direction and a size bucket and nothing else. Canaries planted in the measured value, the target, the metric id, its command and watched path, and the goal body never reach the model input, the stored work items, the ledger events about the model or the output of `omf goal tick`. A model that leaks canaries on its own has each such candidate rejected and none of it stored; a forbidden key voids its whole response. Positive controls prove the canaries existed on the host. The decision-text part of the W side of E2 is `W-decision-no-metric-leak.test.ts`; the verifier and implementer side is later in M3. | §4.6 (F6) |
| `E3-budget-no-reset.test.ts` | Budgets accumulate in the host ledger, never reset on restart, and only people declare or raise them. At tick level: a restarted process keeps the rounds and disclosure already spent, a tick with none left never calls the reconciler, and rounds come back only through a person's raise and resume. Truncating the ledger is not detected, and moving the checkout starts a new project (spec §8). | §4.4, §6 J8 |
| `E4-unevaluated-is-undetermined.test.ts` | A guardrail that was not evaluated is not a passing guardrail: with no bands file, or a baseline that is still too short, a goal never becomes a success candidate however long it is observed; it does once the guardrail evaluates `pass`. Pulled forward from M3; the verification-evidence half of E4 stays in M3. | §4.5 (F7) |
| `E5-init-non-pollution.test.ts` | `omf init` and `omf doctor` write nothing to the repository, `~/.claude`, `~/.claude.json` or `~/.codex`, even when the agent CLIs they probe would | §11 rule 1 |
| `ledger-tamper-stops.test.ts` | Every command (`ledger verify`, `doctor`, `init`, `goal new\|audit\|measure\|tick\|status\|resume\|cancel`, `metric propose`, `work list\|show\|approve`, `veto`, `budget show\|declare\|raise`, `decide add\|resolve\|defer\|lint\|show`) verifies the ledger chain, stops on a broken chain, leaves the ledger unchanged and creates no file. Truncation is not detected (spec §8). Commands added later join this test. | §8 |
| `W-gate1-open-blocks.test.ts` | GATE-1 never passes with a decision not closed by a person. Zero decisions, a missing `interface`, an open required decision, a deferral that `omf` wrote instead of a person, an expired deferral (injected clock, exact second; a person can then resolve it and GATE-1 passes again), an intent whose open questions are not all closed (seeded or not yet seeded), and a record that a goal re-lock made leak each give `blocked_on_user` (J2) with the matching reason. For zero decisions and for unclosed intent questions, `omf decide lint` then exits 3 and persists `needs-human.json` with `default: null`, and a person closing the last item clears it without another lint. After a goal re-lock, lint exits 1 (lint problems win over the block) and the persisted record leaves out the id of the invalid decision. A `record_invalid` or `ledger_anomaly` block names cancel or veto as the only way out: v0.1 has no general reopen, only a deferral can be closed again. | §5.0, §6.2 |
| `W-gate1-then-gate2-walk.test.ts` | GATE-1 takes no link input: an item whose decisions are all resolved and none linked passes GATE-1 and lint without links, so the link rule cannot deadlock it. A local GATE-2 stub sends the same item back to S2 for the unlinked decisions and lists quantitative decisions as `not_run`. The real seal and GATE-2 walk is an `it.todo` until M3c. | §5.0 |
| `W-spec-projection.test.ts` | `spec.md` is a projection of the decision ledger: byte-equal to the render of the verified ledger after every `decide` verb; a hand edit is reported as `spec_drift` by `omf decide lint` (exit 1) and overwritten by `lint --render` and by the next write; it is never read back (a forged `spec.md` changes no state, verdict or output, and `show` writes nothing); concurrent writers leave the render of the final ledger. | §5.1, §5.2 |
| `W-decision-human-only.test.ts` | Only a person closes a decision. The writers refuse `omf` and `agent:*` actors for resolve, defer and n/a and append nothing; a closing event that `omf` or an agent appended directly leaves the decision open and blocks GATE-1; `omf decide resolve\|defer` with piped stdin exits 2 and writes nothing. Not detected, and not tested: a `human:*` event appended by someone who can write `~/.omf` with a recomputed hash chain. The chain does not protect against write access and v0.1 signatures are not cryptographic (spec §8). | §5.2, §6.2, §8 |
| `W-decision-no-metric-leak.test.ts` | The decision-text part of the W side of E2. A full metric phrase or id, the locked target value or its integer part, a number equal to a measured reading, a numeric `response_measure.threshold` equal to the target or a reading, and an id carrying a metric phrase are refused by add, resolve and defer (planted in a question, rationale or deferral default; add and resolve also cover a QAS field, a measure's metric name and an interface argv element); without a re-lock no canary reaches `spec.md`, any `decision.*` event (the rejection of a leaking id keeps only a hash of it), `needs-human.json` or CLI output (after a re-lock, `omf decide show` and `lint` mask the id of an open decision that now leaks, but `needs-human.json` still prints it); `spec.md` names no goal and no e-mail address; after a goal re-lock a record that now leaks is withheld from `spec.md`. Positive controls: the canaries exist in the goal file and the ledger, and a threshold that is neither is accepted. Not detected: near values, paraphrases, a single stem of a multi-stem metric id, stems of a watched path, and a lone single digit (0 to 9) equal to a reading or to the integer part of the target (a lone digit is refused only when it equals the locked target itself, A16a). | §4.6 (F6) |
| `W-ledger-requires-w-event.test.ts` | A W state needs its `omf` W event in the ledger. A hand-edited `in_progress`, `awaiting_review`, `failed` or `done` (no writer exists before M4) is malformed (`w_event_missing`), a forged `work.started` by `human:*` or `agent:*` does not satisfy it, and the item is absent from `verifiedItems.items`, so dispatch, the WIP cap and STOP_IF never see it. Three hand-edited `awaiting_review` items do not trip `back_pressure`; three with their events do. | §6.2, §11 rule 5 |
| `W-outcome-state-table.test.ts` | The outcome of a W run decides the item's state through one table (`OUTCOME_ROWS`), and nothing else does. For each of the six rows a real item goes through `beginRun`, `start` and `finish`: `success` and `flawed` submit to `awaiting_review` (recommendation `merge_recommended` and `not_recommended`, no reason code), an exhausted `flawed` or `blocked` fails the item, `blocked` and `manual` write `work.parked` and leave the item `in_progress`. Each row writes exactly its one event after `work.started`, releases the claim, moves along edges the transition table already has, and only a submit adds to the `STOP_IF` pile. A `manual` park makes the next run throw `needs_human`; a `blocked` park does not. | §5.6, §6.2 |
| `W-claim-crash.test.ts` | A killed run leaves a stale claim and nothing else. A child process (environment from `harnessEnv`, never the real HOME) starts an item through `beginRun` and `start`, announces, and is killed with SIGKILL. While it lived a second `beginRun` threw `claim_held` and appended nothing. After its `exit` the next `beginRun` reclaims the claim, records `work.claim_reclaimed` with the dead pid and `work.resumed` with the new run id, reports `resumed`, and the ledger holds exactly one `work.started`. Not tested here: a pid reused by an unrelated process. | §8, §11 |
| `W-ledger-ahead-repair.test.ts` | A crash between the ledger append and the file write leaves a file exactly one W edge behind the ledger, and only that mismatch is healed. `omf work list` reports such an item (exit 1) and changes nothing. Any `beginRun` on the goal heals it under its own claim and records `work.repaired` with the source event, without anyone naming the item; a run on the item itself repairs it and then continues (`work.resumed`); the result verifies; a second entry finds nothing to heal; an item under a live claim is left alone until the claim is gone. The reverse (a file ahead of the ledger) and a hand edit are never repaired: see `W-ledger-requires-w-event.test.ts`. | §6.2, §8 |
| `W-stop-if-reachable.test.ts` | `STOP_IF` and the WIP cap are reachable through real W flows. Three runs that end in `awaiting_review` (one `success`, two `flawed`) make the next `goal tick` return `back_pressure` / `stop_if_unreviewed_evidence` with zero reconciler calls and zero rounds spent. Two submitted items plus a parked one do not (the parked one is open work, so the tick waits on the cap instead); an exhausted failed item adds nothing; an item whose file is one edge behind its `work.submitted` event still counts as awaiting review, and one behind its `work.started` event fills the WIP cap although the verifier keeps it out of the item list. A goal that is `blocked_on_user` cannot start a run (`governance`). | §6.1 |
| `W-no-complete-in-m3.test.ts` | Nothing in M3 writes `done`; that is a person's act in M4. The store object has no completing method and `repairWorkItem` refuses `done`; no `OUTCOME_ROWS` row and no W event type leads to `done` and `work.completed` does not exist; a scan of `src/` finds the literal `"done"` on a line of code only in the type, the transition table, the verifier and the reconciler's counts, and finds no assignment of it anywhere; `omf --help` and its command groups list no complete, ship, done, finish, merge or accept verb; a W run over every outcome row leaves no `done` item. Not detected: a write that builds the state name at run time. The scan is a tripwire, not a proof; the store test is the proof for the store. | §6.2 |
| `tests/core/lock-contention.test.ts`, `tests/core/ledger-contention.test.ts`, `tests/core/budget-contention.test.ts` | Concurrent processes never both hold the lock, never break the chain, and never both spend the last budget round | §4.4, §8 |

The leak tests use `tests/helpers/reconciler-stub.mjs` in `leaky` mode and the planted strings in
`tests/helpers/canary.ts`. A change to what the goal loop discloses is a change to E2: update the
test in the same commit.
