# oh-my-factory (OMF): M2b addendum, the goal loop

- Status: decisions taken while building milestone M2b (`omf goal tick` and its loop guards)
- Date: 2026-10-12
- Language: English only. The spec, `docs/design/2026-10-12-omf-v0-design.md`, is unchanged except for the §9 command table and a pointer before §4.5. Where this addendum and §4.4 differ in detail, this addendum describes the loop as built.

Spec §4.4 describes the goal tick in six lines. Building it meant answering 30 questions the spec leaves open: what a round is, how success becomes mechanical, which events a tick writes, who may stop and resume a goal. This file records each answer and its reason, the spec gaps the owner should confirm, and what is deferred. The decisions keep their numbers (D1 to D30) because commits, tests and the plan refer to them.

## 1. Decisions

| # | Question | Decision | Why |
|---|---|---|---|
| D1 | Fingerprint and idempotency key | `fingerprint = sha256(canonicalize({goal_id, title: normalizeTitle(title), paths: sortedUniqueNormalizedPaths}))` and `work_id = "w-" + first 12 hex`. Creating an id that exists is a no-op. Dedupe runs against every work item of the goal in any state, so a vetoed item is never proposed again (`src/work/fingerprint.ts`). | Deterministic and restart-safe: a crash between "item written" and "event appended" heals on the next tick. Prose is not hashed, so rewording a rationale neither defeats nor causes dedupe. A paraphrased title is not detected: a known limit. |
| D2 | Station set, round, breaker count | The G stations are `audit`, `measure`, `reconcile`, `dispatch`, `refresh`. A round is one tick that called the reconciler (D18). Every station outcome yields a signature `station\|outcome_class\|normalized_reason`; counts accumulate since the last `goal.resumed` or `goal.approved`; three hits escalate to J6 (`src/goal/signatures.ts`). `ok` signatures embed the tick's progress signature, `waiting` outcomes are not counted, and the stall check runs only immediately before a reconciler call. | The spec states two "3" rules over one data model. Counting every outcome is adopted (Kilroy counts only failure classes), without making normal operation trip it. |
| D3 | Termination mapping | The four states belong to the goal run, not to every tick. A tick returns `continue` or a termination state. `blocked_on_user` and `failed` are resumable by a person; `finish` and `cancelled` are final. `paused` (GATE-4) belongs to W and is unused (`src/goal/run-state.ts`). | Otherwise the four states are unreachable from a cron-driven tick. A stopped goal refuses ticks, which keeps the J6 default "stay stopped". |
| D4 | Risk-class input at reconcile time | Candidates declare literal `affected_paths`. `classifyRisk` judges them against default high-risk globs and the locked metrics' watched paths, expanded through `git ls-files` for directories. An empty or invalid declaration is `high` (fail closed). W recomputes the class from the real diff and may only raise it (`src/work/risk.ts`). | No diff exists at G time. The model chooses paths; code chooses the class. |
| D5 | Item approval step and its J number | `omf work approve <work-id>` (terminal, human actor, typed confirmation) moves `awaiting_approval` to `ready` and records `work.approved`. It carries no J number. | The spec's `decision_required.j` enum has no item-approval J, and inventing "J9" would edit the judgment map. See O3. |
| D6 | Gap size leak | The reconciler sees a direction and a 3-value size bucket (`small`, `medium`, `large`) for a build-mode gap, and a severity (`elevated`, `severe`) for a band breach. Never a value, number, unit, metric id, name, command or path of a metric (`src/goal/gap-summary.ts`). A call that discloses consumes 1 `disclosure` unit when a disclosure budget is declared, immediately before the model call. Without a declared disclosure budget, re-seeds are bounded by `rounds` only. | Coarse buckets leak about 1.6 bits per call; direction alone would starve the model of "how big". E2 tests whatever is sent. See O2. |
| D7 | Where intent.md and work items live | Host state: `goals/<goal_id>/work/<work_id>/item.md` and `intent.md`. Never in the repository. Export of `intent.md` into an opt-in repository directory is deferred to M4. | Spec §11.1 forbids repository state; §5.1 says people commit `intent.md`, which is a human step. |
| D8 | Reconciler invocation and credentials | See section 2. | |
| D9 | Two-turn proof against `min_observation: 7d` | A success candidate needs: the current measurement meets the target, every guardrail passes (or the goal has none), no pending regime change, a streak of at least `MIN_CONSECUTIVE_MET = 2` such `goal.measured` events in this regime, and `now - first_in_streak >= prereg.min_observation`. All time comes from an injectable `now` (`src/goal/success.ts`). The result is recorded as `goal.success_candidate` with `attribution: "before_after"` (correlational). Consequences: a guardrail whose metric has no bands file is never evaluated, so such a goal can never succeed; a goal with an evaluated guardrail needs at least `MIN_BASELINE_POINTS + 1` in-regime measurements; a re-approval starts a new regime and restarts the streak. | Keeps the four §4.5 conditions mechanical and the walking skeleton testable. `examples/hello-goal/README.md` shows the whole path. |
| D10 | Handoff packet on J6 | M2b emits `goal.escalated` (J code, reason code, question, options, default, signature) plus a printed list of exact next commands, and keeps it in `omf goal status`. The full §6.3 packet is M4. | `blocked_on_user` must tell the person what to do next; the packet schema needs ship and evidence that do not exist yet. |
| D11 | `veto` and `budget raise` | Both are built, minimally: `omf veto`, `omf work approve`, `omf budget show\|declare\|raise`, `omf goal resume\|cancel\|status`. | Step 5 needs an asynchronous veto; J8 has no other CLI; resume and cancel are the only way out of a stopped goal. |
| D12 | Stubbed reconciler for hello-goal | A third reconciler kind, `command`, runs a configured argv with the prompt on stdin and JSON on stdout (`src/adapters/reconciler.ts`). | Tests and the example run the whole loop without an external service. |
| D13 | Conformance suite | Not built. The store tests are written as a reusable `runStateStoreContract(name, makeStore)` (`tests/helpers/store-contract.ts`) so M3 can lift them. | `packages/conformance` is not in the roadmap row. |
| D14 | STOP_IF threshold, count and config scope | `STOP_IF_UNREVIEWED_EVIDENCE = 3`, an exported constant (`src/core/config.ts`). The count is the work items in `awaiting_review`, checked before the model call; W writes that state in M3. A missing `config.toml` is a `ConfigError`; only missing sections take defaults. Only `[reconciler]` is parsed in addition to `[isolation]` and `[roles]`; `[stop_if]`, `[refresh]` and `[risk]` are rejected with "not configurable in M2b". `goal.tick_started` carries `config_sha256`. | Spec §11.5 forbids falling back to defaults when config cannot be read. Threshold edits would otherwise leave no ledger trace. |
| D15 | Events and band-breach candidates | A band breach with action `propose` goes through the same reconciler (`trigger: "breach"`) in both modes. `diagnose` and `runbook:*` routes are recorded, not executed. Ticketing and channel events are out of v0.1. | A tool-using diagnosis needs sandbox design (M3), and no runbook registry exists. |
| D16 | Gap trigger | `gap` is build mode with the target not met. `breach` is any metric whose band action in this measurement is `propose`. A work item may be created only if a trigger exists (spec §4.3). | |
| D17 | A tick with no trigger | No model call, no work item, no round consumed. Build mode with the target met evaluates success (D9): all four conditions hold, then `goal.success_candidate` and `finish`; otherwise `observing` with the missing condition as reason code. Watch mode without a breach is `idle`. | Being at target does not excuse a breach. Waiting is not a failure and must not trip the breaker or the stall check. |
| D18 | Round accounting | A round is consumed only by a tick that calls the reconciler: `budget.consumed(rounds)` is appended immediately before `reconcile.requested`, together with `disclosure` when declared; both are checked before either is consumed. Waiting ticks consume nothing and are bounded by wall time (D26). When any open item is `awaiting_approval`, `omf goal tick` exits 1 and lists `omf work approve <id>`. | A watch goal is idle by design and runs indefinitely at low frequency. Charging idle ticks would exhaust J8 after `rounds` ticks while cron saw exit 0. See O1. |
| D19 | Scope ("inside the approved goal scope") | In v0.1 the scope is the repository, bounded by candidate path validation (relative, no `..`, not `.git`). A `scope` goal field is deferred to v0.2. | A real field would change the J1-locked schema and needs a regime migration. |
| D20 | Open questions in a candidate | They do not block dispatch (F8 is enforced at GATE-1 in W). They are stored as `has_open_questions` for the veto view. | The G side has no decision ledger. |
| D21 | Stale goal | Staleness is computed at the end of a tick and recorded as `goal.stale` (`src/goal/refresh.ts`). `isMarkedStale` (a `goal.stale` after the latest `goal.approved`, `src/goal/stale-mark.ts`) makes the audit add a regime-change reason, so the next tick escalates J1 `stale_goal` and `omf goal approve` writes a new approval at regime + 1 even when the semantic is unchanged, which clears the mark. | Matches "the next tick starts with a J1 re-interview". Without making the mark a regime change, a stale goal passes audit cleanly and nothing could clear it. |
| D22 | Approach text input | The reconciler receives `objective` and the `## Approach` section of `goal.md` only, each passed through seed lint. A failure escalates J1 `approach_unusable`; the fix is to edit `goal.md` and run `omf goal resume`. Forbidden metric names are the full id and its multi-token phrase variants, plus a single stem only when it contains a digit or is the id's only stem. | `goal.md` prose may legally contain metric ids and values. Banning every stem would reject most real objectives and starve the loop. Ordinary single words are part of the documented paraphrase limit. |
| D23 | Tick concurrency | One tick per goal at a time, through `goals/<goal_id>/tick.lock` (`src/goal/tick-lock.ts`). A second tick exits 2. `goal cancel` and `goal resume` take the same lock. | An in-flight tick must not create items after `goal.terminated(cancelled)`. |
| D24 | Unexpected exception after state was mutated | Append `goal.terminated` with `failed` and `internal_error`, then rethrow (exit 2). | `failed` needs a producer, and machine faults must not be retried silently. |
| D25 | Candidate filter order | Per candidate: scope, seed lint, fingerprint, WIP cap, risk. The spec lists fingerprint, WIP, seed lint, risk. | A lint-failing candidate must not occupy a WIP slot or claim a fingerprint in the batch. See O8. |
| D26 | Wall time is a J8 cap | `goal.wall_time_raised {goal_id, by}` (human only) is added to the approved wall time (`src/goal/wall-time.ts`). `omf budget raise <goal> wall_time <duration>` writes it. `wall_time_exceeded` is a J8 escalation. Re-approval still refuses to change the wall time in `goal.md`, and raises made before a re-approval do not carry over (`wallTimeLimitMs`, see O4). | Without a raise path, "continue" after a wall-time stop was false: resume re-escalated and re-approval refused, so cancel was the only exit. |
| D27 | The ledger is authoritative for item approval, veto and cancel | `item.md` is a projection. `verifyItemAgainstLedger` marks an item malformed when its state or risk class cannot be derived from `work.created`, `work.approved`, `work.vetoed` and `work.cancelled` (`src/work/ledger-verify.ts`). Malformed items are never dispatched and are listed by `omf work list`, which then exits 1. | Hand-editing `state: ready` or `risk.class: normal` would be a silent approval (§6.2). |
| D28 | Two locks per item | `item.lock` is a millisecond mutex taken by every store write. `claim.lock` records long-lived ownership by a W run (`src/work/claim.ts`). Veto and cancel take `item.lock` only, so they succeed under a live claim and from every open state. | With one lock, a veto was refused exactly while the item was being worked, and a W run could not call its own store. |
| D29 | `goal tick` output carries no values | stdout, stderr and `--json` contain only the outcome, direction, size bucket, work ids, signature codes, next steps and the report path. Targets and measured values stay in the host tick report. | Ticks run under cron and CI whose logs other agents may read (spec §4.6). |
| D30 | Crash healing for work items | `work.created` is appended before the item files are written (`src/goal/reconcile.ts`). A re-run that finds the event but no item writes the item without a second event. An `item.md` with no event is malformed (D27) and is never healed. | A heal that signs unrecorded items would launder hand-made ones. |

## 2. The reconciler (spec §7 gap)

The spec names `reconciler` only in `[roles]`. M2b decided:

1. **Kind** comes from `config.toml [reconciler] kind`: `claude` (default) or `command`. `kind = "codex"`, `roles.reconciler.vendor = "codex"` and `auth = "login_file"` are refused ("needs a container; M3"). A read-only Codex sandbox keeps shell and read tools, so the model could read reports or vault locks (F6); copying an OAuth login file into a second home risks refresh-token rotation signing the user out.
2. **Tool-less, ephemeral, one-shot, host-side.** The host runs `claude` with every tool disabled, no session persistence, an empty scratch directory as its working directory (never the repository), a stripped environment, a timeout, an output cap and a process-group kill. Permission-bypass flags are never used (spec §7). The run is labeled `host, tool-less` and recorded in `reconcile.requested`.
3. **The argument vector** is built by `buildClaudeArgs` in `src/adapters/reconciler.ts`; the prompt goes on stdin. A response reporting more than one turn or any tool use is rejected as `tool_not_disabled`. Unverified: the `claude` kind has not been run against a real model in this milestone; `scripts/smoke-reconciler.sh` is the manual check.
4. **The configuration home is per run**, inside the scratch directory, removed in `finally`. There is no persistent home and no credential copying; the user's `~/.claude` is never read.
5. **Credentials: `api_key` only.** Only `ANTHROPIC_API_KEY` passes through. OMF never stores it. A missing key is an `auth_missing` outcome and nothing is spawned. `scripts/smoke-reconciler.sh` is the manual check of this path against the real CLI.
6. **Kind `command`** runs a configured argv with the same stripped environment, plus names listed in `env_passthrough`. Tests and `examples/hello-goal/README.md` use it.
7. **Untrusted data.** The prompt says every data block is untrusted. The output is parsed as data, validated with `schemas/reconcile-output.schema.json`, linted and re-rendered by OMF, so the model never writes front matter, files or commands. Parse failures are recorded as fixed codes, never as the exception message.
8. **Audit copies.** The exact input and the raw output are kept in host state, mode 0600, under `goals/<goal_id>/reconcile/`.

## 3. Spec gaps and owner decisions to confirm

- **O1** Round accounting (D18): a round is consumed only by a tick that calls the reconciler, and waiting ticks are bounded by wall time. The owner may prefer the literal "one round per tick".
- **O2** An undeclared `disclosure` budget (D6): re-seeds are then bounded by `rounds` only. The alternative is to require a declared disclosure budget before the first reconcile.
- **O3** Item approval has no J number (D5).
- **O4** Wall time as a J8 cap, raised by a human `goal.wall_time_raised` event (D26). A re-approval drops earlier wall-time raises (rounds raises stay in force), and the J1 screen does not show them, so a long-running goal that goes stale (D21) is re-approved into an immediate J8 `wall_time_exceeded`. The owner may prefer to carry raises across regimes, or to show the limit in force on the J1 screen.
- **O5** Subscription and keychain logins are unsupported for the reconciler in M2b; local use needs `ANTHROPIC_API_KEY`.
- **O6** The spec lists `veto`, `approve` and `answer` as M4; M2b builds the minimal ones (D11).
- **O7** `smol-toml` is a new dependency, used to read `config.toml`.
- **O8** The candidate filter order differs from spec §4.4 (D25).
- **O9** A mechanical success candidate ends the run in `finish` (D3), and nothing clears it: `goal resume` and `goal cancel` both refuse it. Until M4 adds J5 sign-off, a candidate the person disagrees with (for example a noisy metric that met the target twice) leaves the goal id permanently stopped. Options: let `goal resume` (human, TTY) reopen a `finish` that has no J5 sign-off yet, or end the run in `blocked_on_user` with a J5-style escalation until M4.

## 4. Deferred

| Item | Deferred to | Reason |
|---|---|---|
| Repository copy of `goal.md` | M4 | Needs an opt-in repository write, which conflicts with the no-repository-writes rule until `ship` exists. |
| A pseudo-terminal test of the J1 prompt, and a J1 re-ask on an unmatched answer | M4 (E8) | Needs a pseudo-terminal harness. |
| Symlinks inside `~/.omf` | M3 | Low risk for user-owned 0700 state; matters when the sealed vault arrives. |
| `diagnose` execution and `runbook:*` routes | M3, M4 | Needs a read-only tool-using model session in a sandbox and a runbook registry. Both are recorded, not executed (D15). |
| Visit caps (3 per station per round) | M3 | G stations run once per tick; the caps need W stations to count. |
| A required image digest for metrics | M3 | Would invalidate approved locks; M2b blocks flag-like images and warns on tags. |
| A goal `scope` field | v0.2 | Schema and J1 regime migration (D19). |
| The full §6.3 handoff packet, `request_human_input`, `omf answer` | M4 | Needs W evidence and the request tool (D10). |
| `omf goal sign` (J5), `ship`, export of `intent.md` to the repository | M4 | |
| Near-duplicate and paraphrase detection | known limit | Canaries and lint catch verbatim leaks and shapes, not meaning (spec §4.6). |
| A single-digit target in the objective or approach | known limit | A standalone digit is allowed by seed lint, so "get it down to 5" with a locked `value: 5` reaches the model; decimals and longer numbers are caught. Writing the target in goal prose is the goal author's leak. |
| W transitions (`in_progress`, `awaiting_review`, `done`, `failed`) | M3 | The table and states exist; M3 adds the verbs and the ledger events `verifyItemAgainstLedger` will then require. |
| Recent outcome aggregates in the reconciler input (spec §4.4 step 4) | M3 | No W outcome exists until M3. M3 adds counts-only aggregates and extends the E2 canary test to them. |
| The `codex` reconciler, `auth = "login_file"` and persistent vendor homes | M3 | They need a container (section 2). |
| `[stop_if]`, `[refresh]` and `[risk]` tables | after a J8 path records their changes | Constants in M2b (D14). |
| Event ingestion, external trackers | after v0.1 (§13) | |
